# 第八轮方案：浮层立刻出现 + 拖动有反馈（2026-11-17 下午）

> 这一轮我先**只做测量，不改代码**，把"到底哪里不对"用数据钉死。
> 结论跟前面几轮很不一样 —— **定位其实已经修好了，剩下的是"交互反馈"问题。**

---

## 一、先纠正我自己的两个错误结论

### 错误 1：我以为"选区只选 9 个字符"是 bug

实测发现**不是**：那是我选中了**标题**（font-size 33，单行 span），
拖 120px 本来就只该选到那么点。正文段落（font-size 22.9）实测：

```
fit:       选中 295 字符 / 4 行 / Δtop = 0px
放大后:     选中 294 字符 / 4 行 / Δtop = 0px
放大再缩小:  选中 295 字符 / 4 行 / Δtop = 0px
```

**定位和跨行都是对的。**

### 错误 2：我以为"卡"是 CPU 慢

CPU profile（真实拖动）：

```
89.4%  (idle)
 4.2%  (program)
 3.5%  drawImage          ← canvas 重绘
 0.6%  exports.jsx        ← React
 0.1%  onSelectionChangeEvent
 0.0%  collectPages
```

页面内原生事件测帧间隔：

```
40 帧拖动: p50=16.7ms  p95=16.9ms  max=17ms  >32ms 的长帧: 0
```

**满帧 60fps，包自己的代码只占 0.1%。CPU 完全不是瓶颈。**

## 二、真正的病根：整个拖动过程**毫无反馈**

### 实测（按住不放，每 100ms 采样）

```
  0ms: 浮层=无  自绘块=0  选区字数=3
100ms: 浮层=无  自绘块=0  选区字数=5
200ms: 浮层=无  自绘块=0  选区字数=7
300ms: 浮层=无  自绘块=0  选区字数=93
...
900ms: 浮层=无  自绘块=0  选区字数=195
松手后: 浮层=有  自绘块=3
```

### 原因

`useTextSelection` 里，**所有**几何计算都挂在 **mouseup** 上：

```
mousedown ──────────────────────────── mouseup ────► 才有选区块 / 浮层
           （900ms 里什么都没发生）
```

而 `selectionchange` 事件**只在 mouseup 时才被处理**（`onMouseUp` 里有完整逻辑，
`onSelectionChangeEvent` 只负责挪哨兵）。

### 为什么用户说"巨卡"

拖动时**完全没有视觉反馈** → 手感就是"卡住了"。
用户必须松手才知道选中了什么 → 如果选错了只能重来。

## 三、方案

### 改动 1：把几何计算从 mouseup 移到 `selectionchange`（核心）

**目标：鼠标一开始动，就出选区块 + 浮层。**

```
现在:  mousedown ────────────────── mouseup ──► 计算 ──► 出浮层
改成:  mousedown ─► selectionchange ─► 计算 ──► 出选区块 + 浮层（跟着手指走）
```

具体：
1. `onSelectionChangeEvent` 里**也跑一遍**完整几何计算（现在只挪哨兵）
2. mouseup 时**不再重复计算**（用脏标记判断，避免双算）
3. 浮层的锚点跟着选区实时更新

**注意**：pdf.js v6 的 `DrawLayer.#selectionChange()` 就是这么做的 ——
它在 `selectionchange` 里实时画选区。我们之前只抄了一半。

### 改动 2：浮层出现时机

| 时刻       | 现在的行为 | 改后                              |
| ---------- | ---------- | --------------------------------- |
| mousedown  | 无         | 无（还没选中东西）                |
| 第一次移动 | 无         | **浮层出现**（哪怕只选了 1 个字） |
| 拖动中     | 无         | 浮层**跟随**选区移动              |
| mouseup    | 浮层出现   | 浮层已在（位置微调）              |

**关键点**：浮层要在**第一次有选区**时就出现，而不是等 mouseup。

### 改动 3：性能保护（避免改动 1 引入新的卡顿）

`selectionchange` 在拖动时会高频触发（实测 30 步触发 15 次），
所以每次都重算会有风险。防护：

| 手段             | 说明                                                  |
| ---------------- | ----------------------------------------------------- |
| **rAF 节流**     | 把 `selectionchange` 的处理推到下一帧，一帧最多算一次 |
| **几何哈希去重** | 选区矩形没变 → 不 `setState` → 不重渲染               |
| **只算可见页**   | 视口外的页不算                                        |
| **基线二分**     | 基线按 top 排序 → 查找 O(log n)（现在是 O(n×m)）      |

**实测过**：现在 JS 只占 0.1%，所以这些是"保险"，不是"救命"。

### 改动 4：哨兵改成不掐死选区（如果确认是它）

我做过对照实验（`display:none` / `pointer-events:none` / 移到页尾），
**选区长度完全一样（17 字符）** → **哨兵不是主因**，先不动它。

但我会再查一次：把哨兵放到"鼠标出界时才生效"，
好处是拖动时它不参与选区计算 → 更干净。**这一项列为可选**。

## 四、改完之后的样子

```
mousedown
   ↓ 鼠标一动
selectionchange（rAF 节流）
   ↓
几何计算 → 选区块实时跟着手指 → 浮层实时出现并跟随
   ↓
mouseup → 浮层停在最终位置（微调一次）
```

## 五、验收标准

| 指标                 | 现在                | 目标                     |
| -------------------- | ------------------- | ------------------------ |
| **拖动中出现选区块** | ❌ 0 个             | ✅ 第一个字就有          |
| **拖动中出现浮层**   | ❌ 无               | ✅ < 50ms                |
| **拖动帧间隔 p95**   | 16.9ms              | 保持 ≤ 20ms              |
| **mousedown → 浮层** | 261ms（且要等松手） | **< 50ms**（且不用松手） |
| 选区与文字 Δtop      | 0px                 | 保持                     |
| 三种缩放状态一致     |                     | 保持                     |
| 链接上拖选           |                     | 保持                     |

**新增 E2E 断言（这次测"手感"而不是"几何"）**：
```js
// 按住不放 → 移动 → 检查浮层已经出现
await page.mouse.down();
await page.mouse.move(x + 30, y + 4);
await page.waitForTimeout(120);
check('拖动中浮层已出现', (await page.locator('.scpdf-selection-popover').count()) > 0);
check(
  '拖动中选区块已出现',
  (await page.locator('.scpdf-selection-layer clipPath rect').count()) > 0,
);
```

**这条断言以前完全没有** —— 所以前几轮"全绿"根本没测到用户真正抱怨的东西。
