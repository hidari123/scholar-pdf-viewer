perf(selection): 性能提优 + 新增性能 E2E

用户要求："性能需要提优"。

## 先测量，确认瓶颈

```
CPU profile:  89.4% idle, 我们的代码 0.1%
帧间隔:       p50=16.7ms  p95=16.9ms  长帧 0 个
```

→ **CPU 不是瓶颈**（满帧 60fps）。
→ 真正的"卡"是**拖动中零反馈**（上一轮已修）。

## 但还是优化了三个 O(n²) 的算法

拖动时 `selectionchange` 高频触发（30 步 → 15 次），每次都跑这些：

| 位置 | 旧 | 新 |
|---|---|---|
| `collectPages` | 每次 `querySelectorAll`（518 span）+ 518 次 `intersectsNode` | **按页分组 + 缓存**（MutationObserver 标脏），一页命中就 break |
| `clipToBaseline` | 每个矩形都 `map`+`filter`+`sort` 整个基线表 | **只保留最近 K=8 个候选**，只排这 8 个 |
| `optimizeClientRects` | 全量双重循环 → 255 矩形 = **65025 次比较** | **先按行分桶**，只在桶内比较 → 几百次 |

### `clipToBaseline` 的候选表

原来的排序键（垂直中心距离 → 水平重叠 → 基线距离）抽成 `compareCandidates`，
配合"只保留 K=8 个"的小表（线性插入维护）。

### `optimizeClientRects` 的分桶

分桶键 = `(pageNumber, 行号)`，行号 = `round(top / 基准行高)`
（基准行高取矩形高度的中位数 → 同一行的 top 抖动会落进同一个桶）。

→ O(n²) → O(n + Σ桶内²)

## 新增 scripts/e2e-selection-perf.mjs（3 项断言）

```
PASS 拖动时满帧（p95 ≤ 20ms，无长帧） - p95=16.8ms
PASS mousedown → 浮层出现 < 150ms - 87.7ms
PASS 多行拖选后有选区块 - 9 个 / 90 字符
```

⚠️ **测帧间隔必须用页面内原生事件**（不能用 CDP 的 `mouse.move`，
那是 RPC 往返，会把测量值放大一个数量级 —— 之前踩过这个坑）。
