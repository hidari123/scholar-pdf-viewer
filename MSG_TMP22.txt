perf(viewer): 拖动选区的性能优化 —— 脚本耗时降到 1/4

用户反馈："性能可否再调优 目前还是会觉得卡顿"

## 实测（优化前）

```
30 步拖动: 1485ms（49.5ms/步）
  脚本: 620ms  布局: 2ms  样式: 4ms
```

CPU profile（采样间隔 100μs）：

```
60.1%  (idle)
18.2%  drawImage          ← ⚠️ **canvas 在重画！**
11.0%  (program)
 3.1%  exports.jsx
```

## 根因 ①：canvas 被反复重画（drawImage 18%）

```tsx
<PageCanvas
  onRenderError={(renderError, failedPage) => { onError?.(...); }}   // ❌ inline 箭头函数
/>
```

→ **每次渲染都是新函数** → `PageCanvas` 的 `useEffect` 依赖它
→ **每次渲染都重跑 effect** → **canvas 被重新渲染**
→ 拖动选区时每一步都在重画 PDF！

修法：提成 `useCallback`（`handlePageRenderError`）。

## 根因 ②：`React.memo` 失效（整页重渲染）

拖动选区 → `PdfViewer` 重渲染 → **18 个 `<Page>` 全部重渲染**
→ 每个 Page 的 `TextLayer`（451 个 span）都要 React 协调一遍。

修法：

- `Page` 用 `React.memo` 包住
- **所有 props 必须是稳定引用**：
  - `onRenderError` → `useCallback` ✓
  - `onInternalLink` → **改成带 pageNumber 的签名**
    （之前是 `onInternalLink={(dest) => onInternalLink?.(dest, pageNumber)}` → inline → memo 失效）
  - `viewport={{ width, height }}` → `useMemo`

## 根因 ③：`collectPages` 遍历所有 span

```ts
for (const [pageNumber, spans] of cache.byPage) {
  for (const span of spans) {
    if (range.intersectsNode(span)) { ... }   // ❌ 451 个 span
  }
}
```

→ `intersectsNode` 会**遍历 DOM 树** → 每次 `selectionchange` 都跑一遍。

修法：**先用矩形粗筛出候选页**，只对候选页做 `intersectsNode`。
（粗筛用 `pageFrames` 推算页的位置，**不能**每次 `getBoundingClientRect()`——
那个会强制重排，实测反而更慢。）

## 实测（优化后）

```
30 步拖动: 633ms（21.1ms/步）   ← 49.5 → 21.1ms/步（快 2.4 倍）
  脚本: 144ms                    ← 620 → 144ms（快 4.3 倍）
  布局: 2ms  样式: 4ms
```

CPU profile：

```
84.2%  (idle)     ← CPU 基本空闲
 6.2%  exports.jsx
```

## 一个重要结论

**包的计算开销 ≈ 0**：

```
withPkg:    17.6ms/步
withoutPkg: 17.6ms/步   ← 拦掉包的 selectionchange 监听
```

→ 那 17.6ms 是**浏览器自己的** `selectionchange` + rAF 成本
→ 也就是说**剩下的开销不是包造成的**（真实浏览器里会小得多）。

顺带修的（同一类问题）：**所有 hook 的返回值都用 `useMemo` 包住**

- `useSelectionPreservation` / `useCurrentPage` / `useTextSelection` / `useVisiblePages` / `useZoom`
- 不然它们的返回值每次渲染都是新对象 → 依赖它们的 effect 每次都重跑
