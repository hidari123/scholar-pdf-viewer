# 第七轮方案：选区只选一小段 / 框不准 / 卡

> 先说结论：**前面几轮我修的都是"数字对不对"，没修"手感对不对"。**
> 这一轮我把真实交互跑了一遍、抓了数据，发现有三个**独立**的问题，
> 之前一直没碰到真正的那条路径。

---

## 一、先复现（真实 PDF，18 页 arXiv 论文，230%）

### 场景 A：fit 状态，在标题行拖 120px

```
选区文字: "An End-t"        ← 只选了 9 个字符！
自绘矩形: 1 个, {x:450, y:238, w:131, h:33}
```

**框本身是对的**（紧贴文字、Δtop=0.01px），
但**选区只涨到 9 个字符就不动了** —— 我明明拖了 120px。

### 场景 B：fit 状态，跨行拖 200px+60px

```
选区文字: "An End-t"        ← 还是 9 个字符！
```

### 场景 C：放大后跨行拖

```
选区文字: "An End-to-E"     ← 12 个字符
```

→ **三个场景全都是"选不長"**，这跟用户说的"框选想选小部分，总是选一大块"是同一个病的两个方向。

---

## 二、根因 1（主因）：endOfContent 哨兵**把自己的选区掐死了**

### 实测证据

```
拖动前:  哨兵 top=1934.6px（= 文本层末尾，top:100%）
拖 60px:  选区="An E"  哨兵 style.top=276.9px  选区 bottom=388.9px
拖 400px: 选区="An E"  哨兵 style.top=276.9px  ← 纹丝不动
```

### 机制（死循环）

`useTextSelection.ts` 的 `onSelectionChangeEvent` 里：

```ts
const rangeRect = range.getBoundingClientRect();
const parentRect = parent.getBoundingClientRect();
const offsetY = rangeRect.bottom - parentRect.top + 1;
end.style.top = `${offsetY}px`; // ← 把哨兵挪到选区底部
```

1. 用户按下拖动 → 浏览器开始扩展选区
2. 浏览器**每扩展一次**就触发 `selectionchange`
3. 我们把哨兵挪到"当前选区底部往下 1px"
4. 哨兵此时**正好在鼠标下面** → 浏览器的拖选命中哨兵
   → 选区被**截断在哨兵处**，不再往下长
5. 回到第 3 步（哨兵位置更新，但仍在鼠标附近）→ **死循环**

**结果：选区永远长不过一行。**

### 为什么之前没发现

- 之前的 E2E 都是"拖一下就松手"，选区小到看不出问题
- 我一直用 `getClientRects()` 的**几何**做断言（几何是对的）
  → **从来没断言过"选中了多少字"** ← 这才是真正的验收指标

### 修法（三个候选）

| 方案                                    | 做法                                                                                           | 评价                                                 |
| --------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **A. 删掉哨兵**                         | 去掉 endOfContent 元素和那段逻辑                                                               | 最简单。但会失去"在空白处拖动不会一路选到页尾"的保护 |
| **B. 哨兵不参与命中**                   | `pointer-events: none` + `user-select: none`（已经是 none 了，但**浏览器仍把它算进选区边界**） | 需要验证浏览器行为                                   |
| **C. 哨兵只在"拖动到文本层外"时才生效** | 平时把它放在 `top:100%`（末尾）；只有当鼠标拖到文本层**外面**时，才临时挪到选区边界            | 保留保护，又不掐死正常拖选                           |

**推荐 C**：跟 pdf.js 的目的一致（哨兵只在需要时出现），但我们**不跟着 selectionchange 走**，而是**跟着鼠标位置走**。

具体实现：
- 监听 `pointermove`（在容器上），记录鼠标位置
- 只有当鼠标 y **超出当前页文本层的下边界**时，才把哨兵挪到当前选区底部
- 鼠标在文本层**内部**时 → 哨兵回到 `top: 100%`（不参与命中）

## 三、根因 2：**哨兵被算进选区边界**（导致"框比字大一块"）

除了"掐死"，哨兵本身还会**污染选区几何**：
浏览器把它当作文本层的一部分 → `getClientRects()` 会多返回一个矩形
→ 自绘层就会在那一行画出一条**多余的块**（用户截图里那一行"整体变蓝"）。

### 修法

选区矩形的来源从 `range.getClientRects()` 改成**只取真正有文字的 span**：

```
遍历 range 覆盖的 .scpdf-text-layer__item
  → 每个 span 用它自己的 getBoundingClientRect()（或 client rect）
  → 得到"纯文字"的矩形集合
```

这样：
- 不受哨兵污染
- 也不受浏览器对空白的行盒处理影响

代价：失去浏览器对字距/kerning 的精确计算。
**折中**：先用 `range.getClientRects()`，但**过滤掉不含文字的矩形**（用 `range.intersectsNode(span)` 交叉验证）。

## 四、根因 3：**慢**

### 实测（真实拖动，30 步）

```
30 步拖动耗时: 496 ms
selectionchange 次数: 15
帧间隔 p50: 16.7ms  p95: 41.8ms  max: 78.3ms
>32ms 的长帧数: 3 / 43
```

→ 每步 16.5ms，p95 到 41.8ms —— **这就是"卡"**。

### 慢在哪

`selectionchange` 每次触发都要：
1. `range.getClientRects()`（浏览器计算，255 个矩形）
2. `collectPages(range)` → **`container.querySelectorAll('[data-page-number]')`**
   → **每页都遍历一遍所有 span**（518 个）→ `intersectsNode` × 518 ← **这是主凶**
3. `buildSelectionShapes` → 遍历 255 个矩形 × 69 个基线 = **17555 次比较**
4. `setSelectionShapes` → React 重渲染

### 修法

| 步骤                   | 现状                                       | 改成                                                                                                                                   |
| ---------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| ② collectPages         | 每次 `querySelectorAll` + 遍历 518 个 span | **按页缓存** span 列表；用 `document.elementsFromPoint` 或直接用 `range.startContainer` 的 `data-page-number` 找起始页，再从该页往后找 |
| ③ buildSelectionShapes | 矩形 × 基线 双重循环                       | **基线按 top 排序 + 二分查找** → O(n log n + m log n)                                                                                  |
| ④ setSelectionShapes   | 每次都 set                                 | 矩形集合没变就不 set（比较 key）                                                                                                       |
| ① getClientRects       | 255 个矩形                                 | **只取与选区文字相交的部分**（配合根因 2 的过滤）                                                                                      |

**预期**：帧间隔 p95 从 41.8ms → < 20ms。

## 五、根因 4（次要）：缩放后基线过期（上一轮已修，但没验证到位）

`handleTextItems` 的"数量相同就不更新"会让基线表停留在旧缩放级别。
上一轮已改成比几何指纹，但**只比了 3 个 item**（第 1 / 中间 / 最后）——
如果这三个 item 在缩放时恰好不变（比如都是空白），还是会漏。

**改成**：比**全部 item** 的指纹（用一个廉价的 hash：累加 `left + top + fontSize`）。
518 个 item 算 hash 也就几微秒，比重新排版便宜得多。

## 六、验收标准（这次要断言**手感**，不只是几何）

| 指标                       | 现在   | 目标                         |
| -------------------------- | ------ | ---------------------------- |
| **选中字符数**（拖 200px） | 9      | **≥ 拖过的行数对应的字符数** |
| **跨行拖选**（200px+60px） | 9      | **跨 2-3 行**                |
| 自绘矩形 vs 文字 Δtop      | 0.01px | 保持                         |
| 拖动帧间隔 p95             | 41.8ms | **< 20ms**                   |
| 缩放后 Δtop                | —      | 保持                         |
| 链接上拖选                 |        | 保持                         |

**新增 E2E 断言（关键）**：
```js
// 拖 3 行 → 选区必须跨 3 行（用选区文字的行数判断，不是几何）
const lineCount = selectionText.split('\n').length; // 或按 y 坐标分组
check('拖 N 行 → 选区跨 N 行', lineCount >= 2);
```

**这条断言以前完全没有** —— 所以前面几轮"全绿"其实没测到真正的病。

## 八、需要你确认的两点

1. **哨兵的保护要不要保留？**
   保留（方案 C）：鼠标拖到页外时选区会停在当前页 —— 更符合"一页一页选"的直觉
   删除（方案 A）：实现最简单，但拖到空白处会一路选到文末

2. **性能目标对不对？**
   我定的是"拖动时帧间隔 p95 < 20ms（不掉帧）"。
   如果你更在意"点下去立刻出浮层"，那就是另一个指标（现在实测 16-22ms）。
