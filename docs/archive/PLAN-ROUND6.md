# 第七轮方案：选区形状（长方形）/ 单行偏移 / 卡顿（2026-11-16 晚 · 修订版）

> 依据：用户明确诉求 + 真实 PDF 实测 + **纯 HTML 对照实验**
> 状态：**只给方案，未写实现**

---

## 一、用户的原话（重新对齐）

> 我想跨行选择 只想选择第一行中间 然后二三四全选 到第五行中间
> 现在又卡 又是只能选择1-5行全部 而且位移偏了
> 之前你那个text-layer选的还是准确的 就是往上偏了一点 现在特别卡 而且全是问题

**拆成 3 个诉求**：

| #     | 诉求                                             | 现状                                              |
| ----- | ------------------------------------------------ | ------------------------------------------------- |
| **A** | 跨行选择：行1 从中间开始，行2-4 整行，行5 到中间 | 浏览器原生行为基本对，但**中间行/末行边界有偏差** |
| **B** | 单行不要"往上偏"                                 | 选区框比字形高 10px，**上下都偏**                 |
| **C** | 不要卡                                           | **17.1ms/步**（慢 7 倍）                          |

## 二、根因（全部实测，含纯 HTML 对照实验）

### 根因 A：跨行形状 —— **是浏览器的行盒模型**，不是我们的 bug

**对照实验**（纯 HTML 页面，绝对定位的 5 行 span，结构与 PDF 文本层一致）：

```
拖 行1中 → 行5中，得到:
  l=348 w=299  t=0     ← 行1: 部分
  l=50  w=597  t=33    ← 行2: **整行**
  l=50  w=597  t=66    ← 行3: **整行**
  l=50  w=597  t=99    ← 行4: **整行**
  l=50  w=298  t=132   ← 行5: 部分
```

→ **纯 HTML 也一样**。这是 Chrome 的行盒选择模型：
**跨行选择时，被"经过"的中间行整行选中；首行和末行按拖动位置精确截断。**

**我们包里的实测**（同样结构）：

```
top=345  left=747  right=1026   ← 行1: 从中间开始
top=498  left=116  right=1305   ← 行2: 整行（浏览器原生）
top=532  left=497  right=926    ← 行3: 整行（浏览器原生）
top=565  left=251  right=1172   ← 行4: 整行（浏览器原生）
top=772  left=255  right=1167   ← 行5: 整行
top=793  left=256  right=709    ← 行6: 到中间
```

**去掉哨兵后完全一样** → **不是我们的哨兵造成的**。
**反向拖（行5→行1）结果完全一样** → 不是方向问题。

> **结论**：用户要的"行1中 + 行2-4全 + 行5中"**浏览器原生就是这样**。
> **问题出在"看起来"** —— 每行的选区**太高（30px 行盒 vs 18px 字形）**，
> 多行连起来就成了一个"大长方形"。

### 根因 B：单行偏移 —— 浏览器用**字体自然行盒**画选区矩形

实测（同一处）：

```
选区 rect:  t=528, h=30
字形墨迹:   535 ~ 553  (18px)
→ 上边多 7px，下边多 5px
```

**CSS 改不动**（实测 7 种）：

| 尝试                               | 选区高             | 文字是否变形          |
| ---------------------------------- | ------------------ | --------------------- |
| `line-height: 1` / `0.9` / `0.62`  | 44 / 44 / **30px** | 否                    |
| `height: 1em` + `overflow:hidden`  | 44px               | 否（但字被裁）        |
| `display: inline` / `inline-block` | 44px               | 否                    |
| `transform: scaleY(0.65)`          | **20px** ✅        | **是（字被压扁）** ❌ |

**唯一的例外是 transform** —— 但那会把字压扁，**不能用**。

> **结论**：**浏览器的原生选区矩形无法贴合字形**。
> pdf.js v6 也一样（它也用 `getClientRects()`）。
> **唯一的解法 = 我们自己画**（我们已经有 SVG 自绘层）。

### 根因 C：卡顿 —— 7 倍差距

```
有哨兵: 50 步 856ms = 17.1ms/步
无哨兵: 50 步 123ms =  2.5ms/步
```

**DOM 操作本身不慢**：

| 操作                                | 耗时        |
| ----------------------------------- | ----------- |
| `insertBefore`（移动哨兵）          | 0.001 ms/次 |
| `getClientRects()`                  | 0.002 ms/次 |
| 整页 `getClientRects()`（323 rect） | 0.20 ms     |

**真凶**：`selectionchange` 每次都把哨兵 `insertBefore` 到选区边界，
而哨兵是 **1408px 宽**的绝对定位元素（`inset: 100% 0 0`）
→ **每次触发整个 text layer 重排**。

## 三、修复方案

### 阶段 1：卡顿（最快见效，风险最低）

| 步骤     | 内容                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |
| **S1.1** | 哨兵改成 **CSS 变量驱动**：不再 `insertBefore` 移动 DOM，只改 `style.top`（绝对定位元素改 `top` → **只重绘，不重排**） |
| **S1.2** | 哨兵尺寸改成 `width: 0; height: 0`（现在 1408px 宽，参与布局）                                                         |
| **S1.3** | `selectionchange` 里只在**目标位置真的变了**时才写样式                                                                 |

**预期：17.1ms/步 → ~2.5ms/步（7 倍）**

### 阶段 2：选区形状 + 单行偏移（核心）

**核心思路：自绘选区层不再用 `getClientRects()` 的矩形，改用我们自己算的"贴合字形"的矩形。**

#### S2.1 精确字形度量（新增 `core/text-layer/glyph-metrics.ts`）

浏览器给的 `actualBoundingBoxAscent/Descent` **偏大**（实测偏 2-9px，因为多数字没有降部）：

```
item                 actual高  真实墨迹高   Δ顶   Δ底
"An End-to-End "         36        28        4    12
"Haoning Wang"           25        18        2     9
"Xia Hu"                 20        15        2     7
```

**方案**：用 **canvas `measureText` 逐字符测量**，
取该 item 内**实际出现的字符**的墨迹上下界：

```ts
// 对 item 文本的每个字符测 actualBoundingBoxAscent/Descent,
// 取 max(asc) 和 max(desc) —— 只有真实存在的字形才计入
// → 得到该 item 的**真实墨迹框**
```

实测验证方向：直接用 `actualBoundingBox`（36px vs 28px）已经**比行盒（44px）好很多**；
逐字符取 max 后能再收窄到接近真实墨迹。

**缓存**：度量结果按 `(fontFamily, fontSize, text)` 缓存 → 同一个字体只测一次。

#### S2.2 自己算选区矩形（新增 `core/selection/geometry.ts`）

**输入**：浏览器选区覆盖的字符区间（`Range` → text item → 字符偏移，用已有的 `mapRangeToItems`）

**输出**：每个视觉行的矩形，**高度 = 真实字形高**，**垂直居中于基线**

```
rect.top    = baseline - inkAscent
rect.height = inkAscent + inkDescent
```

**首行/末行按字符偏移精确截断**（水平方向用 item 的 `left` + 字符宽度累计）。

> 这样：
> - 单行选区 = 一条**贴合字形**的细条（18px，不是 30px）
> - 跨行选区 = **一行一条细条**，行间有空隙 → **不再是大长方形**

#### S2.3 自绘层改用新矩形

`SelectionLayer` 的输入从"浏览器 rect"换成"我们自己算的 rect"。

> **注意**：浏览器仍然负责"用户选到了哪些字符"（我们无从得知），
> 我们只负责"把这些字符画成什么样的矩形"。

### 阶段 3：修高亮叠加 & 选区残留

| 步骤     | 内容                                                                                 |
| -------- | ------------------------------------------------------------------------------------ |
| **S3.1** | 选区清空时**同步清 `selectionShapes`**（现在只设不清 → 旧选区残留，实测 layer 仍=1） |
| **S3.2** | 加高亮后调 `clearSelection()` → 触发 `onSelectionChange(null)` → 自绘层清掉          |

## 五、需要确认（1 个关键点）

**跨行选择的形状**：

- **(a) 一行一条贴合字形的细条**（行间有空隙）
  → 能看清每行选了哪一段，**不会误以为选了一整块**
- (b) 保持连续（无缝）

我推荐 **(a)** —— 这正是你现在看到的"大长方形"的解药。

其余我按实测最优方案定：
- 单行选区高度 = **真实字形高度**（18px 而非 30px）
- 哨兵**保留**但改成 CSS 变量驱动（保住"空白处不选出一大片"的行为，去掉重排）
- 中间行整行选中 = **浏览器原生，不改**（所有 PDF 阅读器一致）
